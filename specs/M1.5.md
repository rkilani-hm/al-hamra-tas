# M1.5 — Application Tracking (ATS Pipeline) (Spec)

## Objective
The ATS core: candidate applications attached to a requisition (M1.2), moving through a CONFIGURABLE stage pipeline with full status history. Builds on M1.2 (application belongs to a requisition) and M0.x foundation. Reuses M0.5 <DocumentPanel> (CV/attachments) and <AuditTrail>. NOT a workflow-engine integration (no submit_workflow call) — it's a candidate entity + application records + a stage state-machine + history.

## Decisions (locked — build to these)
- Candidate model: a SEPARATE tas_candidate entity. Applications link to it (one candidate → many applications over time; feeds the future M1.3 talent pool).
- Stages: CONFIGURABLE. A tas_pipeline_stage table (seeded with a sensible default ordered pipeline), editable later — NOT a hard-coded enum. Stage transitions are config-driven.
- Bilingual: candidate-facing/display fields bilingual where natural; stage names bilingual; all UI EN/AR + RTL. Internal notes EN-only is fine.
- Kuwait context: candidate nationality + nationality_class (reuse tas_lookup 'nationality_class' from M0.2: Kuwaiti/GCC/Expat) captured on the candidate — needed later for Kuwaitization reporting. No quota logic in M1.5, just capture the data.

### RPCs (security definer, transactional — in migration or paired _rpc.sql)
- generate_application_ref() returns text — APP-YYYY-NNNN.
- create_application(p_requisition_id uuid, p_candidate_id uuid, p_source text): validate no duplicate active application for (requisition, candidate); set current_stage to the lowest sort_order active stage (e.g. 'Applied'); insert tas_application + initial stage_history row (from null -> Applied); audit_log('M1.5','application.created',...). Returns application id.
- move_application_stage(p_application_id uuid, p_to_stage_id uuid, p_note text): validate target stage active; write stage_history (from current -> to, moved_by = caller via JWT where available); update current_stage_id; if target stage_type in ('hired','rejected','withdrawn') set application.status accordingly + is_terminal handling; audit_log. Idempotent-safe (no-op if already at target).
- set_application_status(p_application_id uuid, p_status text, p_reason text): hold/withdraw/reject directly (sets status + rejection_reason; logs history + audit).
- list_applications(p_requisition_id uuid, p_stage_id uuid, p_status text, p_candidate_search text, p_mine boolean, p_limit int, p_offset int): filtered, paged. p_mine filters owner_user_id = caller (gate on currentUserId in UI). null filters ignored.
- application_detail(p_id uuid): application + candidate + current stage + stage history + requisition summary.
- list_pipeline_stages(): active stages ordered by sort_order.
- upsert_candidate(...) OR plain PostgREST CRUD for tas_candidate (your call — keep simple; a create/update path for candidates).
Grant EXECUTE to authenticated on read RPCs + create/move/status (recruiter actions) — these are authenticated-usable now (unlike M1.2's service-role-guarded writes) since recruiters operate the ATS; keep stage config (tas_pipeline_stage writes) service-role. Comment M3.1 for per-role refinement.

## Edge cases to handle
- Duplicate active application (same candidate + requisition): blocked by partial unique index + friendly bilingual message in create_application.
- Moving to a terminal stage (hired/rejected/withdrawn): set application.status accordingly; allow but record.
- Candidate with null email: allowed (partial unique handles it).
- "mine"/owner views: gate on currentUserId, stub when null (Entra last).
- Stage reorder/deactivate: don't break existing applications pointing at a deactivated stage — deactivation hides it from new moves but existing apps keep their stage; comment this.
- Requisition not approved/published yet: allow applications? Default ALLOW (recruiters may pipeline candidates early); do not hard-block on requisition status. Note it.
