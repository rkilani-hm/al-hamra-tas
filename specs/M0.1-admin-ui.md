# M0.1-admin-ui — User & Access Administration UI (Spec)

## Objective
The admin surface that lets a SYSTEM_ADMIN provision and manage TAS users: create/edit tas_user records, assign/remove the 7 seeded roles, and assign/remove org scope (Entity -> Branch -> Department) per user. This turns "only the bootstrap admin can get in" into "the admin onboards the whole recruitment team." Tables already exist from M0.1 (tas_user, tas_role, tas_user_role, tas_user_scope, tas_delegation); this builds the management RPCs + UI on top.

## Context / why now
Entra SAML sign-in is live (M0.1-signin). Access is PRE-PROVISIONED: an Entra user with no active tas_user row hits /no-access. So the admin must be able to create a tas_user (by email matching their Entra identity) + assign roles + scope BEFORE that person can use the system. The bootstrap admin (rkilani@alhamra.com.kw, SYSTEM_ADMIN) is seeded; this UI lets them provision everyone else.

## Decisions (locked)
- Admin writes go through authenticated SECURITY DEFINER RPCs that ENFORCE the caller is SYSTEM_ADMIN (check via current_user_roles()/a role check inside the RPC). This makes them work NOW for the signed-in admin (definer bypasses the still-service-role table policies), WITHOUT waiting for M3.1. The in-RPC SYSTEM_ADMIN check is the authorization gate.
- Reuse existing M0.1 tables — do NOT create new identity tables. Reuse the ScopeDrawer / org pickers from M0.2 where they exist.
- Pre-provision by EMAIL: admin creates a tas_user with the person's alhamra.com.kw email; when that person signs in via Entra, resolve_current_user matches them by email. (Document: the email must match what Entra sends.)
- Bilingual + RTL; this is an internal admin tool.
- Delegation management (tas_delegation) — include a light view/create if straightforward; otherwise defer to a note (don't over-scope). Roles + scope assignment are the must-haves.

## Requirements

### Migration — supabase/migrations/<14-digit ts after all existing>_m0_1_admin_rpc.sql
(Timestamp after the latest existing migration — check supabase/migrations/, sort after it.)
RPCs (SECURITY DEFINER; EACH begins by asserting the caller is an active SYSTEM_ADMIN — resolve caller via auth.jwt() email -> tas_user -> tas_user_role -> role code 'SYSTEM_ADMIN'; raise 'not_authorized' if not):
- admin_list_users(p_search text, p_status text, p_limit int, p_offset int): list tas_user with their roles (aggregated) + scope count. Paged, filtered. 
- admin_get_user(p_user_id uuid): one user + full roles + full scopes (+ delegations if included).
- admin_upsert_user(p_id uuid, p_email text, p_display_name_en text, p_display_name_ar text, p_status text, p_default_locale text): create or update a tas_user. On create, email required + unique (citext). Returns user id.
- admin_set_user_status(p_user_id uuid, p_status text): active/inactive/suspended (match the tas_user status check).
- admin_assign_role(p_user_id uuid, p_role_id uuid) / admin_remove_role(p_user_id uuid, p_role_id uuid): manage tas_user_role (ON CONFLICT (user_id, role_id) DO NOTHING for assign; delete for remove). Guard: cannot remove the LAST SYSTEM_ADMIN role from the LAST admin (prevent lockout) — if removing would leave zero active SYSTEM_ADMINs, raise 'cannot_remove_last_admin'.
- admin_assign_scope(p_user_id uuid, p_entity_id uuid, p_branch_id uuid, p_department_id uuid) / admin_remove_scope(p_scope_id uuid): manage tas_user_scope (entity_id NOT NULL; branch/department nullable for broader scope). 
- admin_list_roles(): the 7 seeded roles (id, code, name_en/ar) for the assignment UI.
Grant EXECUTE to authenticated on all (the SYSTEM_ADMIN check inside is the gate). No storage.buckets SQL. ON CONFLICT matches indexes (rubric 12 — tas_user.email is PLAIN unique; tas_user_role PK is (user_id, role_id); tas_user_scope has id PK only, no natural unique -> idempotent via existence check or just insert).

## Edge cases
- Last-admin lockout: admin_remove_role / admin_set_user_status must refuse to remove the last active SYSTEM_ADMIN (raise friendly error). Critical.
- Duplicate email on create: friendly "a user with this email already exists."
- Non-admin reaching the admin routes: route guard + nav hidden (defense in depth — RPC also rejects).
- Email casing/domain: store/match consistently (citext handles case); note email must match Entra.
- Scope with entity only vs entity+branch+department: all valid; UI explains the breadth.
- currentUserId now REAL (post sign-in): the caller resolution in the RPCs uses the JWT email; works for the signed-in admin.
