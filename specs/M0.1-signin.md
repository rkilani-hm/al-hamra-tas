# M0.1-signin — Entra SAML SSO Sign-In + Identity Resolution + Bootstrap Admin (Spec)

## Context
Lovable Cloud has registered Microsoft Entra ID as a SAML SSO provider in Supabase, routing the email domain alhamra.com.kw to Entra. Supabase now trusts Entra-authenticated sessions. This module wires the APPLICATION layer: the sign-in flow, mapping the authenticated SSO identity to a tas_user, seeding the bootstrap admin, app-wide auth context, and route guards — so currentUserId finally resolves and the gated paths across all 12 modules activate.

Auth model (LOCKED, from M0.1): Entra authenticates (who you are); TAS owns authorization (tas_role/tas_user_role/tas_user_scope decide what you can do). SSO identity maps to a tas_user by EMAIL.

## Decisions (locked)
- SSO via supabase.auth.signInWithSSO({ domain: 'alhamra.com.kw' }) — SAML, NOT signInWithOAuth. Sign-out via supabase.auth.signOut().
- Identity resolution: match the authenticated Supabase session's email (from user_metadata/email — sourced from the SAML user.mail claim, fallback to the UPN/name-id email) to a tas_user row by email (citext). 
- Access model: PRE-PROVISIONED. A signed-in Entra user with NO matching active tas_user row sees a clean "No access yet — contact your administrator" screen. We do NOT auto-create tas_user rows on first login (HR system; Al Hamra controls access). EXCEPTION: the bootstrap admin is seeded directly.
- Bootstrap admin: seed a tas_user for rkilani@alhamra.com.kw with the SYSTEM_ADMIN role + a top-level (entity-wide or all-scope) tas_user_scope, so the first sign-in can administer everyone else.
- currentUserId resolution: a single source of truth (auth context / hook) that resolves the session -> tas_user.id, exposed app-wide, replacing the null stubs.
- This module does NOT implement per-role write RLS (that's M3.1). It makes identity REAL; M3.1 enforces authorization on writes next.

## Requirements

### Migration — supabase/migrations/<14-digit ts after all existing>_m0_1_signin_bootstrap.sql
(Timestamp after the latest existing migration — check supabase/migrations/, sort after it.)
- Seed the bootstrap admin idempotently (ON CONFLICT matching the tas_user email unique index — NOTE the partial unique on email WHERE email IS NOT NULL, so ON CONFLICT (email) WHERE email IS NOT NULL [rubric 12]):
  - insert tas_user (email='rkilani@alhamra.com.kw', display_name_en='Rami Kilani' or similar, status='active', default_locale) — idempotent.
  - insert tas_user_role linking that user to the SYSTEM_ADMIN role (resolve role id by code='SYSTEM_ADMIN'); ON CONFLICT DO NOTHING (match the user_role unique).
  - insert tas_user_scope giving that user a top-level scope. Use the broadest scope our scope model supports (e.g. entity-level for the seeded entity, or a NULL/all-scope row if the model treats null entity_id as "all"). If unsure how "all scope" is represented, scope to the seeded primary entity AND note it; admin can broaden later. ON CONFLICT DO NOTHING.
- An RPC resolve_current_user() RETURNS the caller's tas_user (id, email, display_name_en/ar, status) by matching auth.jwt()->>'email' (and fallback claims) to tas_user.email (citext, active). SECURITY DEFINER, granted to authenticated. Returns null/empty if no matching active tas_user (the "no access" case). This is the SERVER-SIDE source of currentUserId — do NOT trust a client-supplied id.
- (Optional helper) current_user_roles() / current_user_scopes() RETURNS the caller's roles + scopes (for the client to gate UI). Granted to authenticated.
No storage.buckets SQL. RLS already exists on tas_user/role/scope from M0.1 — ensure authenticated can SELECT their own resolution via the SECURITY DEFINER RPC (don't broaden table RLS here).

### Auth layer — src/features/auth/ (or src/lib/auth)
- AuthProvider / useAuth context: wraps the app; tracks the Supabase session (supabase.auth.getSession + onAuthStateChange); on session present, calls resolve_current_user() to get the tas_user; exposes { session, tasUser, currentUserId, roles, scopes, loading, signIn, signOut }.
- signIn(): supabase.auth.signInWithSSO({ domain: 'alhamra.com.kw' }) -> redirect to Entra. (Domain configurable via a constant.)
- signOut(): supabase.auth.signOut() + clear context.
- REPLACE the existing null currentUserId stubs: wherever modules currently read a null/hardcoded currentUserId (workflow inbox, notification bell, my interviews/approvals, own-draft creates, recruiter actions, OfferPanel/etc.), source it from useAuth().currentUserId. Grep for currentUserId across src/ and wire them to the context. (Do this carefully — it's the activation of every gated path.)

### Routes / guards
- src/routes/auth.signin.tsx -> "/signin": a clean bilingual sign-in screen with a "Sign in with Microsoft / Al Hamra account" button calling signIn(). RTL-aware.
- src/routes/auth.callback.tsx -> "/auth/callback" (or whatever Supabase redirects to): completes the SSO session (supabase handles the token exchange; this route waits for session then routes to app or to /no-access).
- src/routes/auth.no-access.tsx -> "/no-access": the "No access yet — contact your administrator" screen shown when a session exists but resolve_current_user() returns nothing. Bilingual.
- Route guard: wrap the /app/* routes so unauthenticated users redirect to /signin, and authenticated-but-unresolved (no tas_user) users redirect to /no-access. Authenticated + resolved users proceed.
- The existing AppShell/TopBar: show the signed-in user's name + a sign-out action (replace any placeholder user indicator).

## Edge cases
- Session present but no tas_user (unprovisioned user): -> /no-access, NOT a crash, NOT auto-create. Clean bilingual screen.
- Bootstrap admin: seeded, so rkilani@alhamra.com.kw resolves immediately with SYSTEM_ADMIN.
- Email claim mismatch (UPN vs mail): resolve_current_user matches on the email claim (user.mail) first, then UPN/name-id; document this.
- Session expiry / sign-out mid-session: guard redirects to /signin; no stale currentUserId.
- Loading race: while session/tasUser resolving, show a loading state — don't flash /signin or /no-access prematurely.
- Modules that previously fail-soft on null currentUserId: now they get a real id — verify they don't break when id is finally present (e.g. own-draft create RLS on tas_offer/tas_requisition now satisfiable; my-approvals/my-interviews now populate).
