# M3.1-step2a — Dynamic Permission Model + Management UI (Spec)

## Objective
Activate the dormant M0.1 RBAC tables (tas_permission, tas_role_permission, tas_role) into a data-driven permission system: a seeded permission catalog, role CRUD, a role×permission grant matrix UI for SYSTEM_ADMIN, and the _has_permission()/_caller_permissions()/my_capabilities() helpers. This is STEP 2a — it builds and PROVES the permission model WITHOUT changing any operational RPC's enforcement (that is 2b). 2a is purely additive: existing requisition/application/screening/interview/offer/config guards stay exactly as they are. SYSTEM_ADMIN always bypasses permission checks.

## CRITICAL FIRST STEP — verify real schema before building
Before authoring anything, READ the actual schema of tas_permission, tas_role_permission, and tas_role (from the M0.1 migration + live types.ts). These were created dormant in M0.1 and their real columns may differ from this spec's assumptions (we have been bitten 4 times by schema drift — email index, status enum, partial unique, status values). Specifically determine:
- tas_permission: does it exist? columns? (key/code? name_en/ar? area/category? description? is_system?)
- tas_role_permission: columns + PK/unique (likely (role_id, permission_id))?
- tas_role: does it have an is_system / is_built_in flag to protect the core 7? a description? 
Adapt this spec's column names to the REAL schema. If tas_permission/tas_role lack needed columns (is_system, area/category, description), ADD them via ALTER in the migration (idempotent, IF NOT EXISTS). Report what you found vs what you added.

## Decisions (locked)
- Permission granularity: coarse-to-medium — per-module keys + a few meaningful split-outs. Proposed catalog (adjust keys to match any naming already present; these are SEEDS, tunable in UI later):
  config.manage, user.admin, requisition.write, requisition.submit, application.write, candidate.write, screening.write, interview.manage, interview.score, offer.write, offer.submit, offer.issue, offer.respond, approval.act, report.view, audit.view
- Default grant matrix (SEEDED defaults, editable in UI):
  - SYSTEM_ADMIN: ALL permissions; is_system role; its core admin perms (user.admin, config.manage) locked-on.
  - HR_MANAGER: config.manage, requisition.write, requisition.submit, application.write, candidate.write, screening.write, interview.manage, interview.score, offer.write, offer.submit, offer.issue, offer.respond, approval.act, report.view
  - RECRUITER: requisition.write, requisition.submit, application.write, candidate.write, screening.write, interview.manage, interview.score, offer.write, offer.submit, offer.respond, report.view
  - HIRING_MANAGER: requisition.write, approval.act, report.view
  - APPROVER: approval.act, report.view
  - INTERVIEWER: interview.score, report.view
  - AUDITOR: report.view, audit.view (read-only posture; no write perms)
- SYSTEM_ADMIN bypass: _has_permission() returns true for any key if caller is SYSTEM_ADMIN — safety floor, can never lock admin out.
- Role CRUD: full (create/edit/delete custom roles). Guards: cannot delete a role any user currently holds; cannot delete an is_system role; cannot revoke user.admin/config.manage from SYSTEM_ADMIN (locked-on).
- Scope: NOT enforced here (helper is permission-only in 2a; scope-tightening is a later flip). 
- NO operational RPC behavior change in 2a (additive only). Enforcement wiring is 2b.
- Reuse _is_system_admin() (canonical, from 20260620120000) for gating the management RPCs — do not redefine.

- Helpers (SECURITY DEFINER, set search_path=public):
  - _caller_permissions() RETURNS setof text — distinct permission keys across the caller's active roles (caller resolved via _caller-from-jwt, reuse the resolve_current_user pattern). 
  - _has_permission(p_key text) RETURNS boolean — true if _is_system_admin() OR p_key in _caller_permissions().
- Management RPCs (SECURITY DEFINER; each asserts _is_system_admin() else raise 'not_authorized'):
  - perm_list_catalog() — all permissions (key, area, name_en/ar, description, is_system), grouped/ordered by area. (read, but admin-gated for the management screen; OR grant authenticated read — keep admin-gated for the catalog management view.)
  - roleperm_list_matrix() — roles (id, code, name_en/ar, is_system) + the set of granted permission keys per role (for the grid).
  - role_upsert(p_id, p_code, p_name_en, p_name_ar, p_description_en, p_description_ar) — create/edit a role. is_system roles: allow name/description edit, but code immutable; never settable to is_system via UI.
  - role_delete(p_role_id) — guarded: raise 'role_in_use' if any tas_user_role references it; raise 'cannot_delete_system_role' if is_system.
  - roleperm_grant(p_role_id, p_permission_id) / roleperm_revoke(p_role_id, p_permission_id) — toggle a grant. revoke guarded: raise 'cannot_revoke_core_admin' if revoking user.admin or config.manage from a SYSTEM_ADMIN/is_system admin role.
  - my_capabilities() RETURNS setof text (or jsonb) — the CALLER's own permission keys (granted to authenticated; every user resolves their own). Uses _caller_permissions() + system-admin → all keys.
- Grant EXECUTE: management RPCs to authenticated (in-RPC admin check gates them); my_capabilities() to authenticated. Helpers used internally.
- No storage.buckets SQL. ON CONFLICT matches real indexes (rubric 12). Recursive CTEs single-UNION (none expected).

## Edge cases
- VERIFY real schema first; ALTER ADD COLUMN IF NOT EXISTS for missing (is_system, area, description). Report findings.
- Deleting an in-use role: blocked (role_in_use) — friendly message; suggest reassigning users first.
- Deleting/altering is_system roles: code immutable, can't delete; name/description editable.
- Revoking SYSTEM_ADMIN's core admin perms: blocked (cannot_revoke_core_admin) — generalized lockout protection.
- SYSTEM_ADMIN bypass: _has_permission always true for admin regardless of grant rows.
- my_capabilities for SYSTEM_ADMIN: return all permission keys (so UI shows everything).
- Empty/duplicate permission key or role code: handle (catalog seed idempotent; role_upsert friendly on dup code).
- NO operational change: confirm requisition/offer/screening/interview/application/config writes behave IDENTICALLY to before (their guards untouched).
