# M1.9 — Offer Management (Spec)

## Objective
Capstone of the ATS MVP. Create a job offer for a candidate who cleared interviews, route it for internal approval through the WORKFLOW ENGINE (M0.3's second consumer — like M1.2 requisition), generate a bilingual offer letter (frozen snapshot, stored via M0.5 documents), capture candidate acceptance/decline, and on acceptance advance the application (M1.5) + flag onboarding-ready. Mirrors M1.2's record+workflow structure. E-sign is a DORMANT adapter (recruiter records acceptance in-app now; a signing provider slots in later).

## Decisions (locked)
- Offer approval USES the workflow engine: submit_workflow('offer', ...). Seed an 'offer' workflow definition with role steps PLUS a CONDITIONAL high-salary step (this is the first real exercise of the Full-v1 engine's conditional-step feature). Threshold placeholder: salary_amount >= 2000 (KWD), configurable.
- E-sign: DORMANT adapter (esign_status pattern, like M0.4/M1.7 adapters). In-app accept/decline works now; provider integrates later when configured.
- Candidate acceptance (MVP): RECRUITER-RECORDED on the candidate's behalf (respond_to_offer called by recruiter). Tokenized/portal candidate self-accept is a later enhancement (M1.4).
- Letter generation: frozen letter_snapshot_json from a template (JD-snapshot pattern) — template edits must NOT mutate an issued offer.
- Offer is SENSITIVE: stricter write posture than M1.5/M1.6 — submit/issue/transition via service-role-guarded RPCs (closer to M1.2). Reads authenticated.
- Bilingual + RTL throughout; salary in KWD; Kuwait contract type (limited/unlimited) from M0.2 lookups.

    step 2: 'role' {"role_code":"HR_MANAGER"}, quorum 1, on_reject 'stop'.
    step 3 (CONDITIONAL): 'role' {"role_code":"APPROVER"} (stand-in for Finance/GM), condition_json {"field":"salary_amount","op":">=","value":2000}, quorum 1, on_reject 'stop'. This step is SKIPPED by the engine when salary_amount < 2000 and INCLUDED when >= 2000 — exercising eval_condition.

Instead: seed a simple default letter as a constant the issue_offer RPC uses if no letter_template_id is set — i.e. no new table; issue_offer builds letter_snapshot_json from offer fields + a default bilingual boilerplate (EN + AR) if letter_template_id is null. Document this. (Keep it simple — a real template system can come later.)
- 6 bilingual in_app notification templates (type_codes): offer.submitted, offer.approved, offer.rejected, offer.issued, offer.accepted, offer.declined — with {{reference}}, {{candidate}}, {{salary}}, {{status}} declared in variables_json. ### RPCs (security definer, transactional)
- generate_offer_ref() -> text (OFF-YYYY-NNNN).
- submit_offer(p_offer_id uuid): validate required fields; set status 'in_approval'; call submit_workflow('offer', p_offer_id::text, created_by, <org context from the application's requisition: entity/branch/department>, jsonb_build_object('salary_amount', salary_amount, 'contract_type', contract_type, 'grade', job_grade_id)); store workflow_instance_id; insert tas_offer_event + audit_log('M1.9','offer.submitted'); notify(). Atomic. Service-role-guarded.
- sync_offer_status(p_offer_id uuid): read linked workflow instance; approved -> offer 'approved'; rejected -> 'cancelled'; returned -> 'draft'; in_progress -> leave 'in_approval'. Persist on terminal; event + audit. Authenticated (derive-on-read).
- issue_offer(p_offer_id uuid): require status 'approved'; build letter_snapshot_json (bilingual: from letter_template_id if set, else default boilerplate using offer fields — title, candidate, salary, start_date, contract_type, probation, terms_en/ar); set status 'issued'; create an M0.5 document record (linked_entity_type='offer', linked_entity_ref=offer id, category='offer_letter') — call the existing M0.5 document mechanism / insert tas_document with storage_provider per the M0.5 fallback (or store the snapshot and let DocumentPanel render it; minimally: record a tas_document row referencing the letter); notify candidate 'offer.issued'; set esign_status: if an esign adapter is 'configured' -> 'pending', else 'skipped'; audit. Service-role-guarded.
- respond_to_offer(p_offer_id uuid, p_decision text, p_reason text, p_signature text): p_decision 'accept'|'decline'. accept -> status 'accepted', accepted_at=now(), esign_status 'signed' (if signature/provided) else leave 'skipped', onboarding_ready=true, move the application via M1.5 move_application_stage to a hired/offer-accepted stage (resolve by stage_type='hired' or code; if none, set application status appropriately; don't crash), notify 'offer.accepted'. decline -> status 'declined', declined_reason=p_reason, optionally leave application as-is, notify 'offer.declined'. audit. (Recruiter-recorded for MVP; service-role/authenticated-guarded.)
- transition_offer(p_offer_id uuid, p_action text): cancel|expire (guarded valid transitions; event + audit). Service-role-guarded.
- offer_detail(p_id uuid): offer + application/candidate summary + linked workflow instance summary + letter snapshot + events. Authenticated.
- list_offers(p_application_id uuid, p_candidate_id uuid, p_status text, p_mine boolean, p_limit int, p_offset int): filtered, paged, null-ignored. Authenticated.
Grant EXECUTE to authenticated on sync_offer_status, offer_detail, list_offers; submit_offer/issue_offer/respond_to_offer/transition_offer service-role-guarded (revoke from public), commented M3.1. ## Edge cases
- High-salary conditional step: salary_amount >= 2000 -> step 3 included; < 2000 -> engine skips it (eval_condition). Verify the seeded condition_json matches eval_condition's expected shape {field, op, value}.
- No active 'offer' workflow definition: shouldn't happen (seeded); if missing, surface error, don't silently lose.
- issue_offer before approval: guard (require status 'approved'), friendly message.
- No hired/offer-accepted stage in pipeline: on accept, resolve by stage_type; if none, set application status sensibly + note; don't crash.
- E-sign unconfigured (default): esign_status 'skipped'; in-app recruiter-recorded accept/decline works.
- Decline then re-offer: allow creating a new offer for the same application (don't hard-block); the declined offer stays as history.
- Expiry: transition_offer 'expire' or a note that expiry enforcement (auto-expire by date) is a later enhancement — for MVP, manual expire is fine.
- currentUserId null (Entra last): created_by/actor null; "mine" filter stubs; recruiter-recorded response path works via service-role; no crash.
