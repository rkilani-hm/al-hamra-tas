# M3.1 (consent) — Data Privacy & Candidate Consent (Spec)

## Objective
Complete the M3.1 Security & Compliance layer's data-privacy / Kuwait-labor-context / consent sub-scope (the RBAC/access-control half is already done in step1/2a/2b). Track candidate consent (data processing, background check, data retention) with grant/withdraw + retention window. Bilingual EN/AR, RTL. New key `consent.manage`. SYSTEM_ADMIN bypasses.

## Data model
- `tas_candidate_consent` — id; candidate_id (fk tas_candidate); consent_type ('data_processing','background_check','data_retention','marketing'); granted boolean not null default false; granted_at; withdrawn_at; retention_until date; source text; notes; +audit +trigger.
- Unique (candidate_id, consent_type) — one row per type per candidate (rubric-12 upsert). RLS authenticated SELECT; writes via SECURITY DEFINER RPCs.

## New key
`consent.manage` seeded (area 'consent') + granted SYSTEM_ADMIN, HR_MANAGER, RECRUITER.

## RPCs (gate consent.manage)
- `record_consent(p_candidate_id, p_type, p_granted, p_retention_until date, p_source, p_notes)` → uuid — upsert per (candidate, type); sets granted_at/withdrawn_at accordingly; audit.
- `list_candidate_consents(p_candidate_id)` → jsonb — all consent rows for a candidate. Read open (authenticated).
- Migration: 14-digit ts sorts last; RLS+grants; ON CONFLICT rubric-12 on (candidate_id, consent_type) unique; no storage bucket literal; no recursive CTE; idempotent.

## Feature — src/features/consent
- api.ts (interim loose-cast), types.ts.
- ConsentPanel embedded in the candidate detail route: shows the consent matrix (type × granted/withdrawn + retention) with grant/withdraw controls (gated) + retention date.
- Capability gating `consent.manage`; reads open; SYSTEM_ADMIN passes.

## i18n
Full `consent.*` namespace EN/AR (ar key-complete).
