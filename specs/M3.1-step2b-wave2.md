# M3.1-step2b-wave2 — Enforcement Flip: Recruiter Core (Spec)

## Objective
Second enforcement wave. Flip the recruiter-core write RPCs (requisition, application, candidate, screening) from their CURRENT guards to data-driven _has_permission() checks. This is the daily-work bulk. Unlike wave 1 (uniform _is_system_admin swap), these RPCs have DIFFERENT current guards, so the change differs per RPC (see below). NOT in this wave: interview scoring + approval acting (assignment-sensitive → wave 3), offer (wave 3). SYSTEM_ADMIN bypasses all (via _has_permission).

## CRITICAL — read each RPC's REAL current authorization before editing
These are CREATE OR REPLACE on existing RPCs (Lovable-reauthor-risk surface). For EACH target RPC: read its current definition from the source migration, reproduce it VERBATIM, change ONLY the authorization handling, keep signature/body/SECURITY DEFINER/search_path identical. Two current-guard categories require DIFFERENT treatment:

A) SERVICE-ROLE-GUARDED today (revoke execute from public; only service-role/SYSTEM_ADMIN-ish path): 
   - submit_requisition, transition_requisition (M1.2)
   For these: add `if not _has_permission('<key>') then raise 'not_authorized'; end if;` AND add `grant execute on function ... to authenticated;` (they were revoked from public/authenticated — must be granted now so permitted roles can call them). This is a LOOSENING (opening to permitted roles).

B) AUTHENTICATED-CALLABLE, NO permission check today (any signed-in user can call):
   - create_application, move_application_stage, set_application_status (M1.5)
   - upsert_candidate (M1.5)
   - create_screening, save_screening_scores, submit_screening (M1.6)
   For these: add the `_has_permission('<key>')` gate at the top. EXECUTE grant to authenticated already exists — keep it. This is a TIGHTENING (newly restricting).

VERIFY which category each RPC is in by reading its actual source migration + current grants — do NOT assume. Report the per-RPC current-guard finding.
