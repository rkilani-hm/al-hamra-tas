# M1.2 — Job Requisition Management (Spec)

## Objective
First module of the recruitment lifecycle. Authorized staff raise a job requisition, route it through the M0.3 approval engine, and on approval mark it ready to publish. This is the FIRST module that CONSUMES the foundation (M0.1–M0.5) rather than building new infra. Most logic is integration; the new surface M1.2 owns is the requisition record, its lifecycle, and a thin budgeted-position concept.

## Decisions (locked — build to these)
- JD content: freeze a bilingual jd_snapshot_json at submit time (template edits must NOT mutate an in-flight/approved requisition).
- Status sync: derive-on-read + persist-on-terminal. M1.2 reads its linked workflow instance status; do NOT make M0.3's act_on_task write back into requisition (keep the engine generic). A sync RPC applies terminal transitions.
- Seed ONE active request_type='requisition' workflow definition (2 steps, role-based) so submit_workflow has a definition to use.
- Budgeted-position (light M1.1): warn-only, never hard-block. No Kuwaitization quota logic here (Phase 3).
- Workflow steps: role + named-user only (NO hierarchy-relative steps — manager designation isn't wired yet).
- Bilingual: JD bilingual (from M0.2 template); internal justification field EN-only by design; all UI EN/AR + RTL.

## Requirements

### Migration — supabase/migrations/<14-digit-ts sorting after all existing>_m1_2_requisition.sql
Tables (UUID PKs, audit cols created_at/created_by/updated_at/updated_by + existing updated_at trigger, status checks, indexes on FKs + lookup cols):

- tas_budgeted_position(id, job_position_id fk->tas_job_position, entity_id fk->tas_entity, branch_id fk->tas_branch null, department_id fk->tas_department null, budgeted_count int default 0, filled_count int default 0, fiscal_year text null, status text check in ('active','inactive') default 'active', +audit). Index (job_position_id, department_id).
- tas_requisition(id, reference text unique, title_en text, title_ar text, job_position_id fk->tas_job_position, jd_template_id fk->tas_jd_template null, jd_snapshot_json jsonb default '{}', entity_id fk->tas_entity, branch_id fk->tas_branch null, department_id fk->tas_department null, headcount int default 1, employment_type text null, contract_type text null, target_start_date date null, salary_min numeric null, salary_max numeric null, budgeted_position_id fk->tas_budgeted_position null, justification_en text null, status text check in ('draft','submitted','in_approval','approved','published','on_hold','cancelled','closed') default 'draft', workflow_instance_id uuid fk->tas_workflow_instance null, requested_by uuid fk->tas_user, +audit). Indexes: (status, department_id), (requested_by), (reference), (workflow_instance_id).
- tas_requisition_event(id, requisition_id fk->tas_requisition on delete cascade, event_type text, from_status text null, to_status text null, actor_user_id uuid fk->tas_user null, detail_json jsonb default '{}', created_at timestamptz default now()). Index (requisition_id, created_at).

RLS: enable on all. tas_requisition + tas_budgeted_position + tas_requisition_event: authenticated SELECT (org-scoped/self; comment "per-role tightening M3.1"); authenticated INSERT of own draft requisition (requested_by = caller resolved via Entra oid/email, same self-scope pattern as prior modules); status-transition writes service-role only. Explicit GRANT SELECT TO authenticated on all three. No SQL touching storage.buckets. Any recursive CTE: exactly one UNION.

Reference generation: a generate_requisition_ref() function returning REQ-YYYY-NNNN (sequence-backed, year-aware).

Seed (idempotent ON CONFLICT DO NOTHING):
- ONE tas_workflow_definition: request_type='requisition', version 1, status='active', bilingual name. With 2 tas_workflow_step rows: step 1 = approver_rule_type 'role', value {"role_code":"HIRING_MANAGER"} OR a Department Head role — use role_code 'APPROVER' (exists from M0.1 seed) for step 1; step 2 = role 'HR_MANAGER'. quorum 1 each, on_reject 'stop' for step 2, 'return' for step 1. (Admins reconfigure later via M0.3 builder.)
- A couple of sample tas_budgeted_position rows for the M0.2 sample positions (clearly marked sample), so the budgeted indicator has data.

### RPCs (security definer, transactional — in migration or paired _rpc.sql)
- generate_requisition_ref() returns text — REQ-YYYY-NNNN.
- check_budgeted_position(p_job_position_id uuid, p_department_id uuid, p_headcount int) returns table(budgeted int, filled int, available int, over_budget boolean). Authenticated.
- submit_requisition(p_requisition_id uuid): validate required fields; freeze jd_snapshot_json from the linked jd_template (title/summary/sections/competencies, bilingual) if a template is set; set status 'in_approval'; call submit_workflow('requisition', p_requisition_id::text, requested_by, entity_id, branch_id, department_id, jsonb_build_object('headcount',headcount,'salary_amount',salary_max,'position_id',job_position_id)); store returned workflow_instance_id; insert tas_requisition_event + audit_log('M1.2','requisition.submitted',...). Atomic.
- sync_requisition_status(p_requisition_id uuid): read the linked tas_workflow_instance; if instance approved -> requisition 'approved'; rejected -> 'cancelled'; returned -> 'draft'; in_progress -> leave 'in_approval'. Persist only on terminal change; insert event + audit. Authenticated (safe read+derive).
- transition_requisition(p_requisition_id uuid, p_action text): actions publish|hold|cancel|close with guarded valid transitions; event + audit. (Service-role/admin guarded; comment M3.1.)
- list_requisitions(p_status text, p_department_id uuid, p_position_id uuid, p_from date, p_to date, p_mine boolean, p_limit int, p_offset int): org-scoped, paged, null filters ignored.
- requisition_detail(p_id uuid): requisition + jd_snapshot + linked instance summary (call/join instance_timeline shape) + recent events.
Grant EXECUTE to authenticated on check_budgeted_position, sync_requisition_status, list_requisitions, requisition_detail; submit_requisition + transition_requisition service-role-guarded (revoke from public), commented for M3.1.

## Edge cases to handle
- Over-budget: warn, allow (config flag allow_over_budget default true). 
- No JD template selected: allow manual bilingual JD entry into the snapshot.
- Changes-requested: requisition returns to 'draft', editable, resubmittable (new submit_workflow run).
- Requester out of org scope: blocked by RLS/validation, friendly bilingual message.
- submit when no active 'requisition' workflow definition: should not happen (we seed one); if missing, set requisition 'blocked'-equivalent (leave submitted + surface error), never silently lose it.
- "mine" filter + requester-scoped views: gate on currentUserId, render sign-in stub when null (Entra wired last).

## Definition of done
- tsc --noEmit exit 0; all routes (new + all prior M0.x) return HTTP 200; ar.json key-complete vs en.json.
- Migration sorts after all existing; new tables have RLS + GRANT SELECT to authenticated; no storage.buckets SQL; recursive CTEs single-UNION.
- submit_requisition atomically freezes JD snapshot + calls submit_workflow + stores instance id + audits.
- RequisitionDetail shows live approval status via the reusable ApprovalTimeline/WorkflowStatusBadge from the real instance.
- sync_requisition_status correctly maps instance terminal states to requisition status.
- Default 'requisition' workflow + sample budgeted positions + requisition.* notification templates seeded idempotently.
- Reuses M0.2 config, M0.3 workflow, M0.4 notify, M0.5 audit/documents — no rebuilt reusables.
- Interim loose-casts (new tables only) commented for post-apply swap; no unsupported integrations.
